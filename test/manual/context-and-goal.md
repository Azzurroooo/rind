# 上下文与目标验收

先完成 [公共准备](README.md)。这些用例验证真实模型的行为，mock/fake provider 的通过结果不算本文件的 PASS。

## C09：RIND.md 真正进入上下文

**前置 / 消耗：** 独立工作区，开启请求 trace；约 3 轮。

**流程：**

1. 在测试 `$env:RIND_HOME/RIND.md` 写入：“当用户要求验收报告时，报告最后一行必须为 USER-DOC-472。”
2. 在工作区 `RIND.md` 写入：“当用户要求验收报告时，在 reports/check.txt 写入两行：第一行 PROJECT-DOC-936；第二行遵循用户级文档的结尾规则。”
3. 启动新会话，只发送“请生成验收报告。”，不要在 prompt 中透露路径或标记，也不要显式要求读取 RIND.md。
4. 检查首个模型请求，再检查实际文件内容。接着将项目文档标记改为 `PROJECT-DOC-582`，在同一会话再次要求生成报告，检查下一轮请求及文件。
5. 关闭后用原 ID 重开，再次生成报告，核验当前文档仍生效。

**通过标准：**

- 首个实际模型请求已经包含两份文档的指令；不能把模型自行用工具读取文件当作自动注入成功。
- 首次生成的文件严格为两行 `PROJECT-DOC-936`、`USER-DOC-472`；后两次第一行变为 `PROJECT-DOC-582`。
- `/context` 与请求证据一致；下一轮使用更新后的文档，旧历史不能覆盖现行规则。
- 启动和查看上下文本身不把空会话落盘；真正对话后正常持久化。

**证据：** 两份文档版本、三轮请求、输出文件和 session ID。若注入正确但模型未遵循，记录“注入通过、行为失败”，整体不标 PASS。

## C10：auto compact 自动触发并保持任务信息

**前置 / 消耗：** 较高。确认模型可容纳当前压缩阈值和工具 schema，执行前记录 `/context` 的窗口与阈值。当前默认窗口 200,000 token、阈值 90%（180,000）；以运行版本为准。目前没有公开的 settings/CLI 阈值开关，不能虚构配置项，也不能修改源码/注入假 usage 来代替用户流程验收。

**流程：**

1. 在新会话的早期输入：“最终交付文件是 result.txt，验收代号 HARBOR-864，不得写入其他文件。现在只确认收到。”在报告中记录约束，但不要把答案写进后续填充材料。
2. 准备多份独立、带编号的合成长文本（不含真实敏感信息），逐轮从正常输入提交，或让模型通过正常文件工具完整读取。要求每轮只简短确认。检查请求证据，避免工具截断导致材料实际未进入上下文。
3. 根据实际 usage 和 `/context` 逐步增加已进入上下文的材料，直至达到阈值，继续一个正常任务步骤；全程不调用 `/compact`。
4. 观察是否自动产生压缩记录，随后发送：“按最早约定写出交付文件和验收代号，不要搜索旧记录。”
5. 关闭并恢复该会话，再问最早的交付约定；检查压缩结果随会话恢复。

**通过标准：**

- `compactions.jsonl` 新增 `reason: auto` 的记录，包含有效来源范围和非空交接内容；若只有 `reason: context_length_error`，只能证明超限恢复，不能证明主动 auto compact。
- 后续实际请求使用交接内容，压缩前的完整长历史不再原样重放；`/context` 的使用量下降，新的压缩窗口生效。
- 模型确实创建 `result.txt`，内容满足 `HARBOR-864`，无越界写文件；恢复后仍能正确回答早期约束。
- 不进入无进展的连续压缩循环；继续输入和退出正常。
- 正常 provider 场景应成功生成模型摘要。若 `strategy` 是 `deterministic_fallback`，单独报告降级原因和连续性结果，不宣称真实模型摘要成功。

**证据：** 压缩前后 usage、请求、compactions 记录、输出文件、恢复后回答。预算内未达到阈值记 BLOCKED（未触发），绝不能用手动压缩或模型声称“已压缩”替代。压缩失败/降级另作为故障恢复子项记录。

## G11：/goal 执行、暂停、恢复与清除

**前置 / 消耗：** 真实模型和临时工作区；多轮。启用本次调用数/时间上限，准备在超限时 `/goal pause` 并中断。每个子项单独判定，不以“设置 goal 成功”代替完整功能通过。

### G11a：设置、自动续轮与完成

**流程：** 在空新会话先执行 `/goal`，再输入：

```text
/goal 按顺序创建 stage-1.txt、stage-2.txt、stage-3.txt，内容依次为 ONE、TWO、THREE。每一轮只创建一个文件并检查内容，然后结束该轮；最后一轮检查全部文件后将目标标记完成。不要一次完成所有阶段。
```

不再发送普通 prompt，观察至完成或达到上限。

**通过：** 首次 `/goal` 显示无目标且不落盘；设置后按原 ID 落盘，目标为 active 并自动开始。至少两个不同 turn ID 的自动执行轮次，文件内容和顺序正确，历史有对应目标检查点。最终 `meta.json.goal.status` 为 `complete`；等候 10 秒无额外调用，目标完成后停止自动续轮。

**证据：** goal 状态变化、turn ID、检查点、tool_calls 和三个文件。若模型一轮包办全部阶段，只能判“完成能力已测，跨轮续行未覆盖”，需保留结果，不能假称续轮通过。

### G11b：暂停与跨进程恢复

**流程：** 另起新目标，要求创建 20 个编号文件、每轮只创建一个，并在每次写文件前通过 shell 等待 3 秒。看到至少一个阶段完成后立即 `/goal pause`；待当前执行终止并稳定 10 秒，记录调用数、文件和 paused 状态。输入 `/exit`，用 `rind --session <id>` 恢复，先观察 10 秒，再 `/goal resume`。看到后续阶段继续后再次暂停收尾。

**通过：** 暂停会取消执行并停止后续轮次；稳定后文件和请求不增长（已经完成的工具副作用不回滚）。重开仍 paused，不自行续跑；resume 保留原目标及已有进度，真正继续执行，无重复的并行目标循环。

**证据：** 暂停前后与重启后的 meta、请求时间、文件快照。未抢到暂停窗口则该子项未覆盖；不无限重试。

### G11c：清除与停止

**流程：** 对 G11b 的目标先 `/goal resume`，执行中 `/goal clear`，等待执行稳定；再 `/goal`，关闭并恢复后再次 `/goal`。

**通过：** clear 后停止自动续轮；目标为空且恢复后仍为空；稳定 10 秒无新目标轮次。已有文件与历史保留，下一条普通对话仍可执行。

**证据：** 清除前后 goal、请求数量、恢复输出及一次正常对话。
